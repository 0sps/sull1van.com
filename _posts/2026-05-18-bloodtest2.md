## My Plan

My plan was pretty simple, just:
1. Command Claude or Codex to delegate an army of subagents to process all my PDFs
2. File by file, comprehensively pull all numeric and non-numeric test results out
3. Create a master datasheet with all these results
4. Run a separate set of agents to check the first agents' work, and report any inaccuracies they find.
5. Create a central dashboard to read and manage all my blood test results

Scope creep is lowkey a problem when AI hands you infinite resources, lol. But since I'd only be checking the work instead of doing it myself, this all seemed doable.

## How it went

### Steps 1-4: Data conversion
This was honestly easier than I expected. Claude and Codex both did a great job dispatching agents and converting the blood test results into an Excel sheet. The cool part is the verification bots didn't find any actual errors, they just flagged places where the wrong units were used, like an ALT test from 2018 in ng/dL while the 2020 ALT was in ug/L. I did a manual spot check across the whole dataset and it looked great.

### Step 5: The Dashboard

With the data in *some* kind of usable format, this was where I got to have fun. I started by asking Claude and Codex to both design a rudimentary visual for the labs. My idea was pretty simple: a dual layout, card-based and list-based, where you pick between the two views and get either one card or one list item per blood test. They always show the *most recent* result and its unit, and they're color coded green or red depending on whether the result falls outside the normal range.

But what counts as a 'normal range'? **Depends who you ask!**
  My results often showed different reference ranges for the same test across the years, which I mostly chalk up to the slight differences in how LabCorp and Quest Diagnostics calculate their normal ranges. Within a single company I didn't see much variation.

  Either way, I built a system for it: each blood test record, both in my backend database and in my spreadsheet, *includes* the reference range the lab gave me at the time of the test. The web UI parses that and shows the *most recent* range. Sometimes a test doesn't come with a range, so the site keeps crawling older and older records until it finds one, and that's the reference range you see on the display.

### The Backend

For backend storage I went with Google Firebase. The only real alternative people seem to use these days is Supabase, and its free tier is awful, while Google's looked better for the long haul. The data model I ended up with is honestly pretty funny.

Firebase gives you 50K reads/writes a day for free. After that it's some absurdly low rate, like $0.03 / 100K reads (don't quote me on that). The other great thing is the 1MB data record limit. **1 megabyte! 😂** That's about 1 million characters. For reference, the Great Gatsby comes in around 240,000. My blood test results are never going to be as long as the Great Gatsby, so **we're storing my entire set of blood test results in one Firestore entry!**

It's safe to say this setup will never cost me a dime. The only open question was what the data should look like when it goes to Firebase. I iterated with Claude and we settled on this schema for the master dataset:
```json
  {
    "schemaVersion": 1,
    "tests": [
      {
        "name": "string",
        "unit": "",
        "range": "",
        "type": "",
        "points": [
          {
            "date": "YYYY-MM-DD",
            "rawResult": "",
            "lab": "",
            "sourceFile": "",
            "testResultId": "",
            "rawRange": "",
            "unit": "",
            "sourcePage": "",
            "reviewStatus": "",
            "verificationStatus": ""
          }
        ]
      }
    ]
  }
```


The schema looked good, but then I realized I was about to store private health data in plaintext, which really should be encrypted. I thought about just encrypting the values, but that's pointless since the metadata (test name, test date) matters just as much. So I settled on a *Base64 AES-GCM ciphertext of JSON.stringify(vaultData)*: turn the whole thing into a string and encrypt all of it.

---

With that it finally looked good. I wired up the Firebase integration and ran a one-time script to push all my data, and it worked on the first try. I've been using the site to track my results ever since.

The Firestore database has basically become my new source of truth. I still make regular exports so the Firestore database and Excel sheet run in parallel, giving me two sources of truth. It's a little extra effort, but I want to be covered in case something gets mangled in the database and my data becomes unusable.


## Closing thoughts

This project was genuinely a lot of fun. I reach for the web app whenever I need to look up a blood test value, and whenever I bump into a new bug or feature idea I can just build it. Over time I've added a ton of functionality, and it's become a really solid home for my data that's also easy to share with other people.

It feeds my obsession with optimizing these numbers, and my biomarkers have kept getting better ever since I built the dashboard. Over the last year I've changed my diet and tried a bunch of supplements to figure out what actually moves the needle, which could be its own blog post. (Update: it IS another post now! [see here](https://sull1van.com/best-liver-of-all-time)) For now I'll stick to how I track all this stuff.
